# 自建注册验证码升级方案（服务端图片点选 + 拼图滑块 + 轨迹分析 + 随机出现）

## 一、Context（为什么做）

线上正被批量注册攻击：截图显示同一 IP `161.118.182.232` 在 6 分钟内连号创建 8 个 `@archived.net` 账号（约 1 个/分钟），现有的自建"点击找图"验证码已完全失效。

**根因（已核实代码）**：

1. `challenge` 响应把目标答案明文下发——`prompt` 直接返回目标 emoji 列表，`grid` 又把每格 `content` 一并返回，脚本做一次 emoji→cell 字符串匹配即可算出答案，零成本通过。
2. 布局由前端 `buildLayout()` 生成（`ClickCaptcha.vue` L66-89），服务端拿不到坐标，只按客户端回传的 `cell_id` 判分——恰好是脚本能推导的字段。
3. 词库只有 12 个词、9 格互不重复，映射唯一无歧义。

**目标**：把自建验证码替换为两种**服务端渲染**验证码，并在注册/发码时随机出现（A/B）：

- **A. 图片点选**：服务端渲染图片，答案（像素坐标）只存 Redis，客户端只回传点击坐标。
- **B. 拼图滑块 + 轨迹分析**：服务端渲染背景与拼图块，客户端回传落点 x 与鼠标轨迹；服务端同时校验落点容差与轨迹自然性。

**硬约束**：

- 只用自建，**不接入** Cloudflare Turnstile / 腾讯 / 阿里云（已存在且用户明确拒绝）。
- **不使用 Docker**。
- 背景**程序化生成**，不新增任何图片素材文件；尽量不新增外部依赖。
- 管理后台新增两个设置：`registration_captcha_mode`（`random`|`image_click`|`slider`，默认 `random`）与 `registration_captcha_difficulty`（`low`|`medium`|`high`，默认 `medium`）。
- **不新增** IP 限频、邮箱域名黑名单、注册奖励延后（用户已明确否决）。

**零新依赖可行性**：`golang.org/x/image v0.41.0` 已是 `backend/go.mod` 的**直接依赖**，且 `golang.org/x/image/draw` 已在 `backend/internal/service/user_service.go` L26 使用；`image` / `image/color` / `image/draw` / `image/png` 在该文件 L12-17 已使用。因此程序化绘制 PNG 无需引入任何新模块。

## 二、设计原则

- **答案永不出网**：响应中既不含坐标，也不含可唯一标识目标的字段；坐标只存 Redis。
- **服务端决定一切**：模式、难度、目标位置、容差全部服务端生成；客户端只回传原始输入（坐标/轨迹）。
- **token 契约不变**：`/auth/captcha/challenge`、`/auth/captcha/verify` 两个端点、`click_captcha_token` 字段、`ValidateToken`/`ConsumeToken` 语义（发码前非破坏性校验、注册成功后一次性消费）**全部保持不变**，因此 `auth_handler.go` 的注册/发码流程零改动。

## 三、契约设计（判别联合，单端点）

保持两个端点路径与响应外层结构不变，用 `mode` 字段区分（前端无需感知后台模式设置）。

**Challenge 响应**（`POST /api/v1/auth/captcha/challenge`）：

```go
type RegistrationClickCaptchaChallenge struct {
    ChallengeID string               `json:"challenge_id"`
    Mode        string               `json:"mode"` // image_click | slider
    ExpiresIn   int                  `json:"expires_in"`
    ImageClick  *ImageClickChallenge `json:"image_click,omitempty"`
    Slider      *SliderChallenge     `json:"slider,omitempty"`
}

type ImageClickChallenge struct {
    Image      string       `json:"image"`        // base64 PNG（无 data URL 前缀）
    Width      int          `json:"width"`
    Height     int          `json:"height"`
    Prompt     []TargetHint `json:"prompt"`       // 依次点击顺序
    ClickCount int          `json:"click_count"`
}

// 只给"颜色+形状"描述，不含任何位置信息
type TargetHint struct {
    Shape string `json:"shape"` // circle|triangle|square|star|hexagon
    Color string `json:"color"` // red|blue|green|yellow|purple
}

type SliderChallenge struct {
    BgImage   string `json:"bg_image"`   // 带缺口背景
    PieceImage string `json:"piece_image"` // 拼图块（其余透明）
    Width     int    `json:"width"`
    Height    int    `json:"height"`
    PieceY    int    `json:"piece_y"`
    PieceSize int    `json:"piece_size"`
    // 绝不返回 target_x
}
```

**Verify 请求**（`POST /api/v1/auth/captcha/verify`）：

```go
type captchaVerifyRequestBody struct {
    ChallengeID string          `json:"challenge_id"`
    // image_click
    Clicks      []ClickPoint    `json:"clicks"`
    // slider
    DropX       float64         `json:"drop_x"`
    Trajectory  []TrajectoryPoint `json:"trajectory"`
}
type ClickPoint      struct{ X, Y float64 }
type TrajectoryPoint struct{ X, Y float64; T int64 } // T=相对拖拽起点的毫秒
```

**服务端以 Redis 中存量的 `Mode` 为准**，忽略客户端传的任何模式字段，防止伪造分流。

**模式决策**：用现有 `cryptoRandomInts`（crypto/rand，勿用 math/rand）。`random` = 50/50 等权；`image_click`/`slider` = 100%。

## 五、后端实现

### 5.1 新增文件

**`backend/internal/service/captcha_renderer.go`** — 程序化绘图工具（零新依赖）

- `renderNoiseBackground(w, h int, seed int64) *image.RGBA`：双色渐变（`color.RGBA` 双点 lerp）+ 逐像素噪声（±8）+ 若干随机半透明几何叠加；每次挑战独立种子，图片永不重复。
- `drawShape(img *image.RGBA, shape string, col color.RGBA, cx, cy, size float64, rot float64)`：自写画圆 / 扫描线填充多边形，支持 circle / triangle / square / star / hexagon；先画到临时 RGBA 再逐像素旋转映射实现旋转。
- `drawPuzzlePiece(img, piece, x, y, size)` / `cutNotch(img, x, y, size)`：圆角方块 + 小圆形凸起，用于滑块。
- `encodePNGBase64(img *image.RGBA) (string, error)`：`image/png` 编码 + `base64.StdEncoding`。
- `cryptoSeed() int64`：从 crypto/rand 取种子喂 `math/rand.New(rand.NewSource(seed))`，避免使用全局 `math/rand`。
- 常量：形状池、调色板。

> 不在图中绘制任何文字：`golang.org/x/image/font/basicfont` 的 `Face7x13` 仅支持 ASCII，中文/emoji 会渲染失败；提示文案改为走 JSON 字段返回，同时避免把答案烘焙进图。

**`backend/internal/service/captcha_trajectory.go`** — 纯函数轨迹打分（便于单测）

- `type TrajectoryPoint struct{ X, Y float64; T int64 }`
- `type TrajectoryParams struct{ MinSamples int; MinMs, MaxMs int64; PassScore float64 }`
- `ScoreTrajectory(points []TrajectoryPoint, p TrajectoryParams) (score float64, ok bool, reason string)`

**硬门限**（任一不满足即失败）：时长 `150ms ≤ T ≤ 10s`、样本数 `n ≥ MinSamples`、时间戳非降、向右位移步占比 ≥ 0.65。

**软特征**（各归一到 0..1 加权求和）：

1. 单调性——向右步占比（接近 1 更好，0.9 封顶）；
2. 速度方差 `std(Δx/Δt)/mean(Δx/Δt)`——理想带 0.2~1.5，≈0（匀速机器人）重罚；
3. 加速度符号变化次数——0 次（机器人）或过多（抖动）扣分；
4. 停顿数（`Δt>120ms`）——0 次可疑、>6 扣分；
5. 纵向抖动 `std(Δy)`——恒定直线扣分；
6. **末端吸附**——最后一步 Δx ≤ 0.35×总位移（防"瞬移到位"）；
7. 时间粒度——Δt 不全等于 16/17ms（防固定 rAF 循环）。

通过条件：`score ≥ PassScore` **且**落点 `|dropX - targetX| ≤ 落点容差`。

**`backend/internal/service/registration_image_captcha.go`**

- `buildImageClickChallenge(difficulty)`：渲染噪声背景 → 拒绝采样（防重叠）散布 6~10 个图标，含**同形异色 / 同色异形 decoy** → 随机旋转/缩放/描边，部分被背景笔刷与弧形线裁切（破坏干净分割）→ 从合法目标中按顺序抽 `ClickCount` 个 → 产出 `ImageClickChallenge` + 答案 `ImageClickAnswer{Targets []{X,Y,Tolerance}, W, H}`（坐标以图标质心为准）。
- `verifyImageClick(payload, clicks, difficulty)`：按顺序逐个校验，"就近匹配最近的目标质心且距离 ≤ 容差"；顺序错、点到 decoy、越界均失败。

**`backend/internal/service/registration_slider_captcha.go`**

- `buildSliderChallenge(difficulty)`：先画满程序化背景 → 在 `targetX∈[size+10, W-size-10]`、`pieceY∈[size+10, H-size-10]` 处挖出拼图缺口 → 把该处像素复制成独立 `piece` 图（其余透明）→ 返回**两张独立 base64**（带洞背景 + 拼图块），`targetX` 仅存 Redis。
- `verifySlider(payload, dropX, trajectory, difficulty)`：落点容差校验 + `ScoreTrajectory`；两者都过才签 token。

## 十、风险与顺序约束

1. **设置先行**：服务读模式/难度，缺失 key 必须安全回退（空值当 `random`/`medium`）。
2. **`SystemSettings` 空值归一化**必须做（见第六节注），否则老后台保存会把设置清空。
3. **Redis 版本**：依赖 `GETDEL`（已用于 `TakeToken`）与 `INCR`/`EXPIRE`，需 Redis ≥ 6.2；本已使用 `GetDel`，风险低。
4. **载荷结构先行**：Redis 侧 payload 扩展要先落地，handler 才能用新字段，否则反序列化丢字段。
5. **前后端契约同 PR 切换**：旧组件读 `prompt`/`grid`，若先删旧字段会白屏——必须后端与前端一起改。
6. **`wire_gen.go` 是生成物**：需同时改 `wire.go` 并同步 `wire_gen.go`（或运行 wire 重生成）。
7. **滑块背景天然暴露缺口 x**：脚本能定位 x，防线落在轨迹分析上——这是设计取舍，非缺陷。
8. **触屏端样本偏少**：low 难度样本下限取 8，避免误伤真实用户。
9. 本轮改动**不执行 git commit**，待用户确认后再提交（上一轮 bug 修复的 8 个文件改动同样尚未提交）。
