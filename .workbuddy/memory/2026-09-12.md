## 视频生成计费逻辑审计（只读梳理，未改代码）

产出：`docs/video-billing-audit.md`

核心结论：
- 视频按「每秒单价 × 时长 × 数量」计费，不统计 token；扣费/落库与普通模型同表 usage_logs（billing_mode=video）
- 存在**两条**计费链路：
  - A 同步网关视频（Grok Imagine）→ `calculateOpenAIVideoCost`（openai_gateway_usage.go:781），走 ModelPricingResolver，**支持渠道定价**，五级优先：group 卡 → 分组视频价 → 回源重试 → 渠道价 → 兜底
  - B 异步视频任务（/v1/video、/v1/media kind=video，Seedance/Wan/MiniMax/Hailuo）→ `videoTaskCostBreakdown`（video_task_billing.go:83），**完全不查渠道定价**，只读分组 video_price_* / video_model_prices
- 发现 2 个 P0：
  1. 异步链路不走渠道定价（能力缺口）
  2. `768p`/`2k` 档位在运行时取不到：CalculateVideoCost（billing_service.go:1966）先用 NormalizeVideoBillingResolutionOrDefault 折叠成三档，LookupVideoModelPrice 再 AnyOrDefault 已无意义 → 静默错价
- P1：时长上限硬编码 15s（不按模型）；兜底单价回退到图片 2K 价（$0.134/秒，无告警）；创建时只预扣 Key 配额不冻结余额 → 漏收口
- 建议优先级：P0-2 先改（1 行）→ 方案 A 补链路 B 渠道定价 → 默认价告警 → 预扣风控

用户偏好：本次要求「只梳理出方案报告，不要修改执行」，先交流。后续改造需先给 A/B 方案确认再动手。

## 时长来源澄清 + 解析加固（同日晚，续）

用户明确：**时长来自 API 参数，不是 prompt**；客户端给的时长若超过模型能力，
「按真实扣费」优于「限制时长」（限制会把正常 30 秒视频砍到 15 秒少收，代价更大）。

计费时长三个来源（优先级从高到低）：上游回传真实时长 > 客户端 API 参数 > 默认 8 秒。
`duration` 为 `auto` / `-1` / 非正数时视为「自动」，不参与计费，交给上游真实时长兜底。

加固改动：
- `video_task_service.go` 新增 `parseVideoDurationSecondsParam` + `videoDurationSecondsFromAny/Number/String`，
  支持参数名 `duration`/`duration_sec`/`duration_seconds`/`seconds`，支持 float64/int/int64/json.Number/字符串("10s"、""10 秒"")
- `media_task_service.go` 与 `video_task_service.go` 两处重复解析统一改为调用该函数
- `video_adapters_vendors.go`：`intAtPath` 支持浮点字符串（"10.0" 原本退化成 0）；
  三个 vendor 查询路径扩容（content/video/data.video/task.video/output.video/usage.video_duration）
- 测试：`TestParseVideoDurationSecondsParam`（12 用例）、`TestIntAtPathAcceptsFloatStrings`

用户偏好补充：**宁可按真实时长偶发多收，也不要用上限钳制导致长视频少收**。

跑测试注意（复用）：`internal/service` 包内 `payment_fulfillment_test.go` 有既有编译错误
（stub 缺 AccrueRegistrationReward），需临时 `mv` 到 /tmp 再跑，跑完务必还原；
`TestOpenAIGatewayService_Forward_WSv2ErrorEventUsageLimitPersistsRateLimit` 是既有 panic，与视频计费无关。

## 图片计费链路梳理（同日晚，只读未改）

用户问「生成图片的计费方式也都有吧」。梳理结论：**图片与视频的缺口恰好镜像互补**。

图片已有（比视频更细的部分）：
- `billing_mode=image`，同表 usage_logs；档位 1K/2K/4K
- `image_billing_size.go`：`ClassifyImageBillingTier` 支持档位名 + WxH（**取长边**，视频取短边，符合各自行业惯例）
- `ResolveImageBillingSize` 优先级 = **上游 output（多张取最高档）> 客户端 input > 默认 2K**，
  带 `Source` 标记（output/input/default/legacy）与 `Breakdown` 混合档位计数 —— 视频没有 breakdown

图片缺口：
1. **无 per-model 价格表**：没有 `image_model_prices`，只有分组三档 flat 价（ImagePriceConfig 1K/2K/4K）。
   视频有 `video_model_prices`
2. **无降档链 + 无告警**：`getImageUnitPrice`（billing_service.go:2007）是 switch 精确匹配，
   配了 1K 没配 4K 就直接掉 `getDefaultImagePrice`，静默错价。视频已有 VideoBillingResolutionFallbacks + warn
