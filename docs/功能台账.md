## 0. 项目定位与部署硬规则（红线，不可变）

- 聚合中转模型服务（fork 自 Wei-Shaw/sub2api，自研生图/生视频/计费/验证码）。
- `origin`=ihero3/threerouter-sub2api（自研），`upstream`=Wei-Shaw/sub2api（仅同步基线用）。
- **绝不用 Docker**。二进制 `/opt/sub2api/sub2api`，systemd `sub2api`，服务器代码 `/home/ubuntu/threerouter-sub2api`，库 `sudo -u postgres psql -d sub2api`。
- 改 Go 必须 `go build -tags embed`（否则前端不嵌入，Web UI 失效）→ 重启 systemd。**先本地 commit/push 再上服务器 `git pull`**。
- 模块根是 `backend/`，在 `backend/` 内执行 `go build ./...` / `go test ./...`。

## 1. 三条常驻 mandate

1. **客户端永不可见上游原文**：上游错误只进 `OpsUpstreamErrorEvent`；客户端文案只来自管理员 `CustomMessage` 或平台统一文案（`openAIUpstreamClientMessage` 等）。`applyErrorPassthroughRule` 已移除 `PassthroughBody` 分支（2026-09-24 闭环）。
2. **Antigravity 基本不用**：除非明确需要，默认走原生 OpenAI/CC/Responses/Anthropic 适配，不依赖 Antigravity 中间层。
3. **只修 bug、不加多余功能**：任何"优化"以稳定性为唯一目标，不引入新能力。

## 2. 功能台账（按模块）

### 2.1 网关与多厂商兼容层
- OpenAI(CC) / Responses / Anthropic / Gemini / Grok 五类上游适配。
- **CC 上游唯一 POST 出口**：`sendCCUpstreamRequest`，统一 `normalizeOpenAICCUpstreamBody`（GLM effort→DeepSeek response_format→reasoning_content 回填，顺序不可换）。新增归一化只加这一处。
- **Responses 上游 6 出口**：Forward/passthrough/WS×2 共用 `normalizeOpenAIResponsesRejectedFieldRetryBody`（预算 6 + sha256 去重）；`forwardAsChatCompletions` 接 `retryOpenAIResponsesRejectedFieldOnce`。
- **自愈登记**：CC `ccUpstreamSelfHealBody`；chat 链路 `openAIResponsesChatPathRetryReasons`——新增自愈原因必须在此登记+补反例。
- **Anthropic 出口**（3 native + `ResponsesToAnthropicRequest`）静默丢 `text.format`/`response_format`——已知未修待拍板。
- **Enum 被拒自愈**（`openai_reasoning_effort_compat.go`）：「上游说了算」——从 400 报文解析允许集就近对齐，严禁厂商档位表；已合法闸门比 raw 字节；nil/内核字段三来源取并集。

### 2.2 推理回传（两条链路，勿混）
- **A. CC→Responses 桥接**（报 `reasoning_text`）：回注**结构化 reasoning item**，不包 `<thinking>`。
  门控 `ShouldReplayToolCallReasoning(model)`（`!= AnthropicStrict`），**勿**收窄成 `== PassbackRequired`（ResolveThinkingProtocol 只认硬编码前缀，后台加模型名会漏判）。
  门控+租户 scope 读写对称，分散在 `forwardAsChatCompletions`/`handleChatBufferedStreamingResponse`/`handleChatStreamingResponse`，各自重算。
  缓存 key 必带租户维度（`reasoningContentTenantScope`，优先 `u<userID>:`）——call_id 客户端可控，不隔离会跨用户串扰（TTL 7 天）。
- **B. CC→CC 直转 `forwardAsRawChatCompletions`**（报 `reasoning_content`）：契约——带 tools 的请求后续所有轮次必须回传 assistant 的 reasoning_content（即使该轮无工具调用）；无 tools 多轮则 200。
  修法 `openai_gateway_cc_reasoning_passback.go`，占位符必须是**单空格 `" "`**（空串 V4-Pro 也拒）。两层：`applyCCReasoningPassback`（预判 gated，接在 `normalizeOpenAICCUpstreamBody` 末尾）+ `ccUpstreamSelfHealBody` 第四类自愈（`isCCReasoningContentPassbackError`）。
  **预判只认 DeepSeek**（platform/model/base_url 三路并集）；kimi/glm/minimax 不预判只自愈。**A 修不覆盖 B**。

### 2.3 错误透传与上游出口地图
- 错误写出口必须 `MarkResponseCommitted(c)`。例外 `writeOpenAIResponsesFallbackError`(cc_pipeline.go) 明确不标记，**勿改**。
- 成功 = 状态成功 AND 产物非空：succeeded 无 URL 绝不结算（否则扣钱不给货回 502）。范式 `grok_media.go:IsGrokVideoStatusBillable`。
- PollTask 超时兜底必须排在 `UpstreamTaskID==""` 判空之前（否则永久卡 processing）。media/video 对称。
- 结算只用 `UpdateStatusIfProcessing` 的 claimed 守卫（并发会重复退预扣）。新增仓库方法同时加 repository+service 两个 interface。
- Grok「200 但 usage 全 0」守卫覆盖 `chat_completions.go`/`chat_completions_raw.go`/`openai_gateway_messages.go`；位置必须在 cyber_policy 哨兵 return **之后**。

### 2.4 支付子系统
- `internal/payment/`：`Provider` 接口、`Registry`、`PaymentType` 常量；`provider/` 下 easypay/alipay/wxpay/stripe/airwallex 五个适配器。
- 渠道白名单 `validProviderKeys` = {easypay, alipay, wxpay, stripe, airwallex}（**无 paypal**，PayPal 零支持）。
- EasyPay 自定义支付方式：实例 `customMethods`（JSON 数组 `{type, upstreamType, displayName}`），`SupportedTypes()` 返回 `[alipay, wxpay] + 自定义 type`；校验 `validateEasyPayCustomMethods`（type/upstreamType 仅小写字母数字下划线连字符，且不得以 alipay/wxpay 开头）。
- 配置 AES-256 加密（`payment.Encrypt/Decrypt`）+ 敏感字段掩码（`providerSensitiveConfigFields`）。
- **PayPal 接入结论（2026-10-12）**：代码四层硬编码零支持；个人 PayPal 无法自动化收款（官方要求 Business 账户）；人工收款走兑换码闭环（管理员 `POST /api/v1/admin/redeem-codes` + `POST /api/v1/redeem`）。海外充值优先复用 Stripe/Airwallex。

### 2.5 异步生图 / 生视频 / 媒体
- 承诺 `/v1/chat/completions`、`/v1/images/generations`(含 edits)、`/v1/videos/generations`(含 `/v1/videos`)；响应结构任何分组一致；`/v1/media*` 与 video-tasks 只读兼容降级。默认图模 qwen-image-3.0；`?wait=N≤180`。
- **异步生图三态（勿回退成二态）**：开关关=404；开+凭证全=转存；开+凭证不全=URL 透传（刻意设计非 bug）；URL 透传拒 b64/data:URI/空；无对象存储+显式 b64_json→400 不扣费；succeeded 无图判 failed；视频产物缺失降级 processing（30min 兜底）。

### 2.6 邀请返利 affiliate
- action：`accrue`=充值返利、`register_reward`=邀请注册奖励、`transfer`=提现（**不是返利**）。只能用 service 常量，勿写 SQL 字面量。
- 计提入口：`payment_fulfillment`（仅 balance/subscription 算 baseAmount）、`redeem_service`、`admin_user`。
- **返利只向上走一级**：`node.rebate_amount` 是给直接上级的，只有 depth=1 才属查询用户。
- 管理端 `GET /admin/affiliates/relations?user_id=`（WITH RECURSIVE ≤10 层防环）+ `/relations/unsourced`。
- 明细全 0 常见原因（均有 `AFFILIATE_REBATE_SKIPPED` 审计）：affiliate_enabled 默认 false、比例 0、无邀请关系、超有效期、到上限、被邀请人没充值。

### 2.7 账号调度 / 限流 / failover
- **跨厂商 failover 状态码同口径**：OpenAI `shouldFailoverUpstreamError`=401/402/403/404/405/429/529/≥500；Gemini 与 Antigravity 各一副本，由 `failover_status_parity_test.go` 锁死——**新增状态码三处一起加**。
- 429 不可永久禁用账号（2026-10-11 回归修复 `c3bb5a308`）：统一交 `handle429` 按平台分流（OpenAI OAuth 重试窗口 / Spark 影子内存冷却 / 国产供应商 `applyCNProviderReactive429` / 其余按 reset 头或兜底秒级冷却），可用性由 failover 保证。

### 2.8 幂等与结算
- request_id/Idempotency-Key 是本网关幂等标识，**永不下发上游**。键序 header>body；重放带 `X-Idempotency-Replayed`；scope：图片异步按 apikey、媒体按 user；上游调用 `context.WithoutCancel`（5xx/超时可能已建任务，靠重放+by-request 找回）。
- 例外：openai gpt-image-* 同步直通、grok 媒体直通 xAI 均无幂等。
- 卡死回收：`IdempotencyCoordinator.Execute` 中 processing 超「ProcessingTimeout(30s)+ProcessingHardCap(10min)」判进程已死→`TryReclaim`；未超宽限绝不回收（防双创建/双扣费）。无显式键时按 `auto:`+`BuildIdempotencyFingerprint` 派生兜底键。

### 3.4 深度扫描新增项（Explore 子代理 very thorough，2026-10-12）
> 结论：**无 P0（无会导致线上崩溃/资损的硬伤）**。以下按严重度，已亲自核对。

- **P1 资金精度（系统性）**：金额全程 `float64` + `decimal(20,2)` 存储，跨币种比价/退款存在舍入漂移与 `math.Abs(paid-expected) > tol` 的浮点比较脆弱性（`payment_fulfillment.go:112`、`payment_amounts.go`）。建议：金额比较/累加统一改用 `decimal` 或整数最小货币单位；本轮未改（属重构，需配套测试，避免动钱）。
- **P2 多币种容差过大**：`paymentAmountToleranceForCurrency`（`payment_fulfillment.go:119`）对 zero-decimal 币种（JPY/KRW）容差达 `0.5`，对 3 位小数币种达半个单位。建议 zero-decimal 收紧到 0（精确整数匹配），按币种最小单位取容差。本轮未改（怕误拒合法支付，需产品确认币种清单）。
- **P2 数据模型缺口（决策项）**：`AdminSubscriptionPlanResult` 响应含 `Currency` 但 `subscription_plans` 无 `currency` 列、生产投影不填充 → 套餐货币编辑静默丢失。需拍板：加列打通，或明确取消套餐级货币（统一全局结算币种）。
- **P2 死代码（已核对，非全部真死）**：子代理报 `RedeemService.GetStats` 无调用方——**误判**，实际被 `redeem_handler.go:375` 调用，未删。
- **P2 latent panic**：除已修的 `req_log` 外，扫描另报 `c.MustGet` 类型断言风险点，已随本次修复消除。
- **P3 `ErrorPassthroughService` 订阅泄漏**：`Subscribe` 用 `context.Background()`，无 `Close()` → 进程级订阅累积。建议补 `Close()` 并在上游 context 取消时退订。
- **P3 `json.Unmarshal` 错误被丢弃**：多处 `cfg` 解析 `if err := json.Unmarshal(...); err != nil { return ... }` 缺失 → 静默用零值。建议至少 `Warn` 记录。
- **P3 affiliate 返利 `roundTo` 用 `float64` 取整**：与 P1 同源，建议整数/decimal。

> 处理原则（ mandate ③ 只修 bug 不加功能 + 稳定优先）：本轮只落地**低风险、确定正确**的修复（死代码、编译恢复、latent panic）。涉及改钱（P1/P2 金额容差）、数据模型/API 契约（P2 套餐货币）、订阅生命周期（P3）的项**标注为待决策/待配套测试**，不擅自改动以免 destabilize。
